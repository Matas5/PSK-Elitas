Implementation plan for Risk List story

Project context:
This project has a Spring Boot backend and React/Vite frontend.

Relevant backend files:
- backend/src/main/java/com/riskmonitor/entity/Risk.java
- backend/src/main/java/com/riskmonitor/dto/RiskStruct.java
- backend/src/main/java/com/riskmonitor/service/RiskService.java
- backend/src/main/java/com/riskmonitor/controller/RiskController.java
- backend/src/main/java/com/riskmonitor/repository/RiskRepository.java

Relevant frontend files:
- frontend/src/pages/Risks.jsx
- frontend/src/components/CreateRiskDialog.jsx
- frontend/src/api/risksApi.js
- frontend/src/constants/risk.js

Important note:
The current Risk entity does not appear to have a category field, but the acceptance criteria requires category. Either add category to the backend entity, DTOs, create/edit forms, and database schema, or confirm with the team that category is handled by another story. Best option for this story is to add category because it is explicitly required.

Assumption:
The Jira issue SCRUM-12 was not accessible, so treat "read-only modal like SCRUM-12" as a Material UI dialog matching the existing CreateRiskDialog style, but with read-only fields and Edit/Delete actions.

Plan:

1. Add backend endpoint to list risks.

Add GET /api/risks in RiskController.

Reason:
The frontend currently only supports creating a risk and fetching one risk by id. The acceptance criteria requires showing all created risks, so the backend needs a collection endpoint.

Suggested implementation:
- In RiskService, add listRisks().
- Use riskRepository.findAll(), preferably sorted by created date or name.
- Return RiskResp DTOs from the controller instead of returning JPA entities directly.

2. Add frontend API methods in frontend/src/api/risksApi.js.

Add:
- listRisks()
- getRisk(id), if the modal needs to fetch fresh details
- deleteRisk(id), if delete is implemented in this story
- updateRisk(id, body), if edit is implemented in this story

Reason:
The API file currently only has createRisk(). Keeping API calls centralized makes the page cleaner and keeps error handling consistent.

3. Update frontend/src/pages/Risks.jsx to load and display the risk list.

On page load:
- Call listRisks().
- Store risks in state.
- Show loading state while fetching.
- Show error state if the request fails.
- Show empty state if no risks exist.

Display each risk with:
- Name
- Category
- Logging frequency
- Unit of measurement
- Evaluation direction
- Risk level thresholds

Reason:
This directly satisfies the acceptance criteria that users can see each risk and its main information.

4. Use a Material UI table or list for the overview.

Suggested UI:
- Use MUI Table, TableHead, TableBody, TableRow, TableCell.
- Make each row clickable.
- Optionally include action icons for View/Edit/Delete.

Reason:
The project already uses Material UI. A table is the clearest layout for scanning many risks and comparing fields. Avoid adding new dependencies unless needed.

5. Add formatting helpers for risk fields.

Create helper functions such as:
- formatFrequency(risk)
- formatDirection(risk)
- formatThresholds(risk)

Direction can be derived from thresholds:
- If upper thresholds exist and lower thresholds do not: Higher value = higher risk
- If lower thresholds exist and upper thresholds do not: Lower value = higher risk
- If both exist: Both directions

Reason:
The backend stores threshold fields, not a single direction field. Formatting helpers keep table and modal labels consistent.

6. Create a read-only RiskDetailsDialog component.

Suggested file:
frontend/src/components/RiskDetailsDialog.jsx

Props:
- risk
- open
- onClose
- onEdit
- onDelete

Show:
- Name
- Category
- Description
- Logging frequency
- Unit of measurement
- Evaluation direction
- Lower thresholds
- Upper thresholds
- Valid from
- Valid until
- Created/modified metadata if useful

Dialog actions:
- Close
- Edit
- Delete

Reason:
The acceptance criteria says selecting a risk should open a read-only modal and allow edit/delete. A separate dialog component keeps Risks.jsx simple and matches the existing CreateRiskDialog pattern.

7. Connect row selection to the read-only modal.

In Risks.jsx:
- Store selectedRisk in state.
- When a user clicks a risk row, set selectedRisk.
- Open RiskDetailsDialog.
- If the list endpoint returns all needed fields, use the selected list item directly.
- If not, call getRisk(id) before opening the modal.

Reason:
This gives the user a simple way to inspect a risk before deciding whether to edit or delete it.

8. Refresh the list after creating a risk.

Currently Risks.jsx opens CreateRiskDialog and shows a success snackbar. After a risk is created:
- Close the create dialog.
- Re-fetch the risk list.
- Show a success notification.

Reason:
The newly created risk should immediately appear in the overview. Re-fetching keeps frontend state consistent with backend sorting and server-generated fields.

9. Implement delete flow.

Backend:
- Add DELETE /api/risks/{id} in RiskController.
- Add deleteRisk(id) in RiskService.
- Check that the risk exists before deleting.
- Return 204 No Content on success.

Frontend:
- Add deleteRisk(id) API method.
- In RiskDetailsDialog, clicking Delete should open a confirmation dialog.
- Only delete after the user confirms.
- After delete, close the modal, refresh the list, and show a success notification.

Reason:
Delete is destructive, so the user should confirm before the risk is removed.

10. Implement edit flow if this story includes actual editing.

Backend:
- Add PUT /api/risks/{id}.
- Add RiskUpdateReq DTO.
- Use the existing Risk.update(UpdateRiskFields modifiedRisk) method.
- Reuse the same threshold validation logic as create.

Frontend:
- Best option: refactor CreateRiskDialog into RiskFormDialog with mode="create" or mode="edit".
- In edit mode, pre-fill form fields from the selected risk.
- Submit using updateRisk(id, body).
- After successful edit, close dialogs, refresh the list, and show success notification.

Reason:
Create and edit use nearly the same fields and validation. Reusing the form avoids duplicated code and inconsistent validation.

11. Add category support if required by this story.

Backend:
- Add category field to Risk entity.
- Add category to RiskCreateReq, RiskUpdateReq, and RiskResp.
- Add validation, for example @NotBlank and @Size(max = 100).
- Make sure the database schema can store the new field.

Frontend:
- Add category field to CreateRiskDialog or RiskFormDialog.
- Display category in the risks table.
- Display category in RiskDetailsDialog.

Reason:
The acceptance criteria explicitly says each risk must show category. The current backend model does not expose one, so this is a required data model change unless the team says otherwise.

12. Add loading, empty, and error states.

Risks page should handle:
- Loading: show spinner or skeleton rows.
- Empty: show a clear "No risks created yet" message.
- Error: show an alert and retry button.

Reason:
The list page should still be understandable when there is no data or the backend request fails.

13. Verify the implementation.

Frontend checks:
- cd frontend
- npm run lint
- npm run build

Backend checks:
- cd backend
- ./mvnw test

Manual checks:
- Create a risk.
- Confirm it appears in the list.
- Click the risk and confirm the read-only modal opens.
- Confirm all required fields are displayed.
- Delete a risk and confirm it disappears from the list.
- Edit a risk if edit is implemented, and confirm updated values appear in the list.

Reason:
This story touches both backend API and frontend UI, so both automated and manual checks are needed.
